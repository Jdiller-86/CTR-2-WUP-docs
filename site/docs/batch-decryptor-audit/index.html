    Batch CIA 3DS Decryptor investigation¶

    Reviewed October 12, 2026 for CTR2WUP 0.16.0. Its decryption methods can fit CTR2WUP's input-preparation stage. Retain the project's original checked engine; accept independently validated decrypted output as an additional input route. Decryption alone does not translate ARM, provide 3DS services, render PICA draws on GX2 or produce a playable Wii U WUP.

    What the software actually does¶

    The original script loops over CIA/3DS inputs. ctrtool inspects CIA title/content metadata, a separate decrypt engine produces decrypted NCCH partitions, and makerom rebuilds decrypted CIA or NCSD/CCI output. Base-game CIA conversion commonly ends in a .cci, not a CXI. .cci and .3ds can both contain NCSD; the magic/layout, rather than renaming, identifies the format. makerom's -ignoresign does not create authentic Nintendo signatures or a Wii U package.

    The readable later engine uses CIA AES-CBC ticket/title-key/content decryption, NCCH AES-CTR section counters, hardware-style KeyX/KeyY derivation, primary versus secondary ExeFS keys, and optional SHA-256 title-seed checks/derivation. It includes shared platform/common-key constants; it does not require a unique personal console key for every ordinary retail title. Some input types still need a particular title key or seed. The exact required material depends on the dump.

    That engine also tries Nintendo seed endpoints when a seed is missing locally, logs derived key-related data, and supports forms outside CTR2WUP's current base-title scope. Those behaviors have not been adopted. CTR2WUP's current route uses explicitly local file imports, redacted diagnostics and no automatic key/ seed download. The final GUI will expose local preparation using that same engine.

    Fit with CTR2WUP¶

    Mechanism Current CTR2WUP position Decision
    CIA outer AES-CBC and ticket/title key Implemented with local file references and full TMD plaintext-content hash checks Keep existing original implementation
    NCCH section AES-CTR / mixed ExeFS keys Implemented for v2 and standard/1/0a/0b methods Same method; no need to launch the batch wrapper
    Seed DB / seed-derived KeyY Local import, seed verification and derivation implemented Keep local/private source; GUI import remains planned
    Decrypted NCSD/CCI output Accepted by magic; main NCCH preparation and asset checks available Useful optional handoff from a user-run decryptor
    Rebuilding a CIA/CCI with makerom Unnecessary for the injector's main executable/asset preparation Do not add a dependency just to repack the source
    Batch convenience Can inform eventual queued input/progress handling Use controlled engine jobs, structured results and isolated outputs
    Fixed-key or NCCH v0/v1, updates/DLC/system/DSi titles Unsupported in CTR2WUP's current preparation profile Separate implementation/evidence needed; no new compatibility claim
    Windows executables Not run in this Linux/cloud audit Native Windows/source-build/provenance tests remain pending

    The original batch performs broad wildcard deletion of NCCH intermediates in its working directory. Redux documents non-ASCII filename limitations and cleanup of decrypted CIAs even when CCI conversion fails. These are concrete integration problems for a GUI that must preserve user inputs and support spaces/ Unicode. CTR2WUP already uses bounded parsing, isolated staging, immutable source checks and atomic non-overwriting publication.

    Reuse and licensing decision¶

    The original MIT wrapper can be adapted with its notice, but adds little to the existing orchestration. Bundling decrypt.exe as an unexplained binary would leave source/provenance and behavior unresolved. Redux's reviewed tree does not supply a blanket redistribution grant for its wrapper and bundled dependencies. The readable Rust engine is GPL-3.0; use would require the applicable source/ license obligations and an explicit integration design. A fork's MIT badge is not evidence that inherited GPL code was relicensed: the reviewed main.rs and ctrutils.rs match the GPL fork's full SHA-256 hashes. This audit does not make a legal conclusion about the publisher; it records why that label is insufficient for choosing a dependency.

    Recommended adaptation: keep CTR2WUP's original decryption/preparation code, use published crypto/layout facts as cross-checks, and validate a user's already prepared CIA/CCI/CXI through the same inspection/full-IVFC/revision path. A future source-built external backend is technically possible, but no integration need or licensing/provenance resolution is established by this audit.

    Verified handoff and remaining proof¶

    An original synthetic decrypted .cci passed inspection -> prepare-rom -> full IVFC -> prepare-assets -> executable-only intake. The prepared blob matched its original bytes, the executable revision survived and the source stayed unchanged. This verifies the supported NCSD/CCI handoff, not execution of Batch Decryptor or its Windows binaries, and not an actual Mario dump.

    A local handoff can use:

    python -m host prepare-rom "MyGame-decrypted.cci" --output "private/prepared"
python -m host prepare-intake "private/prepared/game.cxi" --output "private/intake"
python -m host prepare-assets "private/prepared/game.cxi" --output "private/assets"

    The standalone v0.5 Windows CIA helper expects CIA; a .cci is handled by the Python engine above, not by renaming it to CIA. When resources are available, the small private intake can be supplied without uploading keys or a full asset blob. Actual user-key exports, Mario input, Windows execution and console gameplay remain unverified. No further resource is needed from the user while away.
