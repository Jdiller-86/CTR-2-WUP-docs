    CTR2WUP product development plan¶

    Finalized 2026-10-07 following the user's request to realign with the supplied preview of “Evaluate 3DS Emulation Viability”, project-brief.md, and the user's UWUVCI AIO GUI workflow clarification. gui-workflow.md specifies the reviewed reference, screens, Inject action, output and acceptance criteria. The referenced conversation supplies product context; its feasibility scores, upstream coverage percentages and compatibility claims are not verified results. The original brief remains the requirements document, with the October 12 user amendment accepting optional local encrypted-input preparation described in encrypted-input.md. This plan corrects the execution priorities and preserves its hardware, correctness and licensing gates.

    Product and completion target¶

    Deliver a Windows GUI, CTR2WUP.exe, with an UWUVCI-style 3DS Inject page:

    Select ROM → configure title/artwork/settings → choose WUP output → Inject → install the resulting WUP on Wii U → launch from the Wii U Menu.

    The GUI runs this conversion sequence behind its Inject action:

    1. Select a user-owned Old 3DS .3ds, .cxi or supported base-application .cia. Use decrypted input directly, or prepare encrypted input locally using material imported from the user's 3DS; validate the recovered executable/assets. No key is bundled or uploaded. Device extraction and GUI import help remain planned.
    2. Detect the title/revision and report its actual support status.
    3. Analyze and translate its ARM/Thumb/VFP code on the Windows PC.
    4. Compile translated code and the reusable Wii U HLE runtime with devkitPPC; stage the game's required assets and shader/state data.
    5. Generate original Wii U metadata and a stable per-game title identity, then produce a validated installable WUP directory and build report.
    6. Install on the documented homebrew Wii U environment and launch from the Wii U Menu, with top screen on TV and bottom screen/touch on GamePad.

    The first MVP supports one exact commercial Old 3DS revision. Completion requires conversion by the Windows GUI, actual WUP installation/Menu launch, repeatable interactive gameplay, input/touch as required, audio, save/reload, rebuild/save continuity and measured useful performance on physical Wii U. Record the supported revision, installer/environment and known limitations. Broad compatibility follows that proof. The CLI remains the shared build engine and an engineering tool. The finished user product is the GUI; normal injection requires no manual shell commands.

    Foundation and scope correction¶

    The version 0.2.0 baseline at commit f42d449 contains useful container inspection, build orchestration, checked guest memory, original CPU tests and native/guest Wii U diagnostics. Commercial build currently stops at an unsupported-profile error; its external lifter adapter performed analysis only. Version 0.3.0 now integrates external C generation and checked static linking/execution; see upstream-integration.md. There is no PICA renderer, commercial runtime or Windows executable distribution. Version 0.4.0 implements an original scoped encrypted writer and independent decrypting verifier; installer acceptance and the commercial pipeline remain unverified. packaging.md defines its exact limits and local-input contract.

    Keep those foundations and use the synthetic guest as a regression test for the conversion/runtime boundary. Direct development effort toward integrating the audited lifter, reusing suitable HLE behavior, producing WUPs and running the selected title. Expand fixtures and CPU/service coverage to resolve concrete adapter, title or console failures. Measure progress by working conversion stages and supported game behavior, with test counts as supporting evidence.

    The planned foundation is the pinned fearkov/3dsrecomp host lifter and license-cleared Zakuro CPU/HLE components or selected behavior ported into a WUT-compatible C/C++ runtime. The current Rust/Vulkan desktop runtime is not a validated Wii U target. Define an explicit portable generated-code ABI and port the required pieces; retain checked little-endian memory and controlled guest scheduling. Normal guest execution uses AOT code, with observable, correct fallback for supported misses. Adopt upstream implementations only after their licenses and target suitability pass the existing audit gates.

    Ordered implementation plan¶

    Phase Work and concrete deliverable Acceptance / original milestone mapping
    P1: Resolve conversion foundations Extend the pinned lifter adapter from analysis to C generation and static linking; normalize its 32-bit ABI, little-endian fast memory paths, SVC/resume state and fallback boundary. Resolve lifter redistribution notices. In parallel, choose a license-cleared WUP packaging route and stage original code/content/meta for the existing native app. Original ARM/Thumb/VFP tests execute through the adapted lifter on desktop and PowerPC; report code size, build/memory costs and fallback timing. Original homebrew WUP is generated and physically installed/launched/exited. Advances M1/M2 and establishes M6 packaging prerequisites.
    P2: Select and analyze the first title Compare a small candidate set using reproduced upstream evidence and service/GPU/module demands. Obtain one user-owned decrypted revision when its private inspection is needed. Extract code, RomFS and required module metadata; create an exact-hash profile and feature/test-route matrix. A selected revision, traceable requirements, repeatable gameplay/save route and explicit unsupported features. Sets the scope for M3–M5. Title analysis can proceed while P1 console tests are pending.
    P3: Run that title through the Wii U runtime Implement or adapt only the required kernel/SVC/IPC/APT/FS/HID/CFG/GSP behavior, guest scheduling and memory layouts. Implement the required PICA-to-GX2 draws, shaders, textures/TEV/transfers/coherency with reference tests. Add exercised CRO relocation/dispatch, DSP/audio and save/extdata behavior. Use targeted redistributable fixtures for each interface. Adapted guest fixture works on console; selected game progresses through boot → menu → gameplay → save/reload. Produce a manually staged per-game WUP through P1 packaging and verify Menu launch. Record physical CPU/GPU/fallback timings, memory, accuracy and stability. M3/M4/M5 acceptance remains evidence-based.
    P4: Automate the Windows injection engine Connect all proven stages to the existing host pipeline: detect encryption → optional local decrypt/validate → profile → extract → translate → compile → shader/cache preparation → link/stage → metadata/title ID → pack → validate → publish. Provide real internal build/rebuild/import-trace/validate-package, versioned GUI requests/progress events, cancellation, revision-aware caches, stable saves/IDs and actionable diagnostics. A clean Windows machine converts the selected ROM into the functioning per-game WUP through the engine without hand edits. Verify install/Menu launch, rebuild/save continuity and uninstall behavior. Completes M6 after its console checks; the CLI alone does not complete the product.
    P5: Deliver the Windows GUI injector Build the C# WPF front end on a supported .NET LTS release over the verified engine, following gui-workflow.md. Provide the UWUVCI-style 3DS Inject page, ROM/compatibility detection, game name and artwork previews, settings/WUP destination, one Inject action, responsive progress/cancellation, completion/SD-install guidance and saved-project rebuild. Package or provision actual prerequisites through documented setup. CTR2WUP.exe performs the supported injection on clean Windows without manual shell commands. Its WUP installs, launches from the Menu and passes the agreed physical-console gameplay/save test. Completes M7 and the first MVP.

    P1 has two independent work streams: translator/runtime portability and packaging. Resolve packaging early so installer, metadata, certificate and key requirements are known before completing the game runtime. P2 supplies the evidence for P3's feature priorities. The GUI workflow is specified now; its implementation follows the demonstrated conversion pipeline. Every engine stage supports the final GUI-driven Inject action.

    Packaging and reuse decisions¶

    The audited nuspacker/CNUS_Packer checkouts have no identified license grant; their certificate templates also lack established redistribution provenance. Find an applicable grant or a suitable licensed alternative. If neither is available, implement an original scoped packer from documented formats with license-cleared cryptographic dependencies. Record the selected route and actual installation evidence before treating packaging as solved.

    Complete 3dsrecomp's missing redistribution notices before bundling its executable or ABI support. Its existing local invocation can support research while this is resolved. Preserve applicable notices for adopted Zakuro code; validate each ported subsystem against the portable ABI and target toolchain. A wholesale desktop emulator port is outside the selected architecture.

    Keys and any required certificate material use documented user-managed local configuration with redacted diagnostics. ROMs, extracted assets, translated commercial code, saves and per-game packages remain private. A structural package pass is separate from signature/installer policy and successful installation.
